## 问题和目标

持续开发由 DSH 承担，项目应保留常规源码、构建、测试和用户文档。旧循环调度、重复需求状态和只看 diff 的评审增加维护成本。测试汇总会漏掉空/缺失轮次，Python 裁剪状态判断错误；这些问题会污染验证结论。

## 范围与职责

Mac-DSH、Mac-Claude、NAS-DSH 按任务认领完整研发工作，实施与独立审查分离，真机操作交 Mac 端；Mac-Codex 只实施本次流程变更。任务和证据标执行端，公开 Git 身份保持 Chamo。

- 私有持续提示词与跨设备交接留在 Git 忽略目录，旧调度脚本退出运行。
- 每项需求只维护本文件，元数据和详细验收放在一起；目录自动生成，PR 链接证据。目录不提供互斥锁。
- 使用 DSH 独立审查，签名报告绑定 base/head、执行端、检查文件、调用链和测试证据。GitHub 仅验证签名、提交身份、隐私与版本，保留 all checks 和 agent-review 必需门禁。
- 修复 ci_report/test-matrix 的缺失轮次、空轮次、重复输入、选择集合缺失和进程退出码处理。
- 复用 #48 的 Python 裁剪修复，核对对照构建的拒绝条件。
- 补全发布包项目文本的隐私扫描；保留构建、依赖锁、许可证、测试与品牌资源。

## 验收

- AC-1：Git 跟踪范围不含私有提示词、日志、凭据或审查私钥；公开文档引用有效。
- AC-2：每项需求仅一份 PRD，目录可重建；负责人有执行端标识；删除旧 PR/JSON 副本与孤立 Docker wrapper。
- AC-3：修改后的测试汇总拒绝合成空/缺失轮次、真实非零退出、重复 XML 和测试集合变化，完整重复通过应成功。
- AC-4：空/已裁剪运行时 pending=false，存在可裁剪内容时 true；prune 保留运行时所需 packaging。
- AC-5：错误签名、陈旧 head/base、缺失检查文件、实现者自审或存在阻塞问题不能给出通过；无报告保持 pending。完整代码审查由未参与实现的另一执行端实际执行并记录证据，不把签名本身当成正确性证明。
- AC-6：三端 CI、包体和发布候选检查保留；Linux/Windows 解包后扫描项目自有文本，缺少隐私配置的正式发布拒绝放行。
- AC-7：NAS 与 Mac 目标实际加载，任务有设备名，NAS 原工作区未被覆盖；新的评审入口在独立审查通过后部署。
- AC-8：首次迁移可由独立审查者 dispatch 现有工作流的已审分支版本。默认分支尚无验证器时，只允许 PR44、指定分支、有效期限内且签名报告绑定该 Actions SHA 的一次性路径；执行前校验已独审快照中验证器、扫描器和公钥的固定哈希。执行只持有 Actions 的内容只读、PR/状态写权限，不能将本机宽权限凭据交给验证器；错误条件或篡改快照须拒绝。默认分支部署后仅使用主干验证器，迁移快照路径退出；实际 main dispatch 成功才算迁移完成，必需检查和正常受保护合并保持有效。
- AC-9：Ubuntu UI 作业在两次依赖下载超时后改用 Ubuntu 官方归档源，保留发行套件、组件、签名配置、软件包与测试范围；实际 runner 必须完成依赖安装并运行 UI 测试。不能将安装超时、取消或仅替换镜像视为测试通过。

## 风险与回滚

评审实现和发布检查属于高影响工具，必须先跑负例并由另一执行端独立核实。切换时沿用 agent-review 状态名；旧评审与新检查器不能只回滚一半。签名私钥只在审查设备，公钥与验证器在可信主干。签名不防止持有管理权限的账号修改仓库规则，权限隔离仍需按实际账号配置评估。

需求变更、流水线和私有规范同步更新；验收结果只写实际执行证据。100% 单测行/分支覆盖仍是质量目标，当前混合报告不等同于达标。
