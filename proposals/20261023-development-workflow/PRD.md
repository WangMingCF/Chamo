# 项目目录整理

## 问题与目标

开发调度、部署配置和 CI 检查混在旧目录，公开文档依赖专用执行提示词。整理为常规项目结构，保留需求登记和有效的质量检查，不修改产品行为。

## 范围

- `scripts/ci/`：隐私扫描、独立评审、维护者审核及对应测试。
- `proposals/`：需求总目录、PR 摘要和详细 PRD。
- `docs/`：架构、开发、测试和版本计划。
- 保留已有覆盖率报告草稿：CI 输出引擎行与分支统计，明确混合测试报告不是单测 100% 的证据。
- 私有持续开发规范与部署交接独立保存，Git 忽略；公开文档不依赖这些文件。
- 退役外部循环驱动及未启用的认领实验，旧文件在本地私有备份中保留。

## 非目标

不新增调度服务，不改产品代码，不降低 CI 或审核要求，不保证单测通过即可证明所有实际功能正确。

## 验收

- AC-1：私有规范不出现在 `git ls-files` 和待提交清单中，公开 Markdown 链接有效。
- AC-2：需求检查器通过；GitHub Actions 使用新路径执行隐私扫描和评审工具测试。
- AC-3：旧路径与新 CI 工具路径均受审核保护；缺少关键词配置继续拒绝推送。提交默认身份符合项目要求。
- AC-4：产品目录没有改动；本地旧资料可恢复，NAS 已有工作区不被覆盖。

## 验证与回滚

本地只检查文件结构、引用、语法和隐私。工具行为由 GitHub Actions 验证，尚未执行的检查不计为通过。路径迁移与工作流引用一并提交；需回滚时恢复整个提交，不能只恢复其中一侧。已部署的可信钩子保持可用，在新工具验收前不替换。

## 风险

CI 路径迁移需要维护者审核。私有规范不随 Git 克隆分发，NAS 同步与运行状态应单独确认。100% 单测覆盖率是后续质量目标，本次不宣称达标。
