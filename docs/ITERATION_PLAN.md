# Chamo 迭代计划（0.2 → 1.11，共 20 个版本）

> 本文件是**可变的任务队列**，不是长期目标本身。长期目标（快、准、小；可信；跨平台）见第 1 节，稳定不变；
> 第 3–5 节的状态、基线与版本条目每完成一轮就按事实更新。写入本文件的每个数字都要能在仓库里复跑。
>
> 编写时间：2026-10-21。编写依据：`main` 上的 `d5c1636`（Chamo 0.1.0）、CI 全绿、旧项目 0.2.0–0.6.2 的研究与基准（本机归档，位置见本地 AGENTS.md）、本轮补测（第 4 节）。

---

## 1. 长期目标（稳定，不随版本改）

1. **准是底线。** 任何发布都不能降低转换正确性。速度与体积的改进必须在质量不回退的前提下取得；不得靠降分辨率、丢内容、缩小测试集或改变对照条件制造收益。
2. **快与小只认实测。** 同机、同样例、重复测量并报告波动；没有对照数据的「更快/更小」一律不写。不宣称未经证明的「第一」。
3. **可信是护城河。** 本地处理、原件不动、绝不覆盖不同内容、来源/成品可核验、有损操作必须主动选择并说明变化。
4. **跨平台但不冒充。** macOS 原生应用 + Windows/Linux 的 CLI 与本机浏览器界面，共用 Python 引擎；界面、调度、引擎、平台适配分层，平台差异集中在 `engine/platform_*.py`。CLI 不得冒充完整 GUI。
5. **不做无据重写。** 没有实测瓶颈和同口径原型对比，不把引擎改写成 Go/Rust 等其他语言。

## 2. 给执行 Agent 的规则（每一轮都适用）

### 2.1 一轮的完整闭环

1. 从第 5 节取**最靠前的未完成版本**（或其中证据最充分、价值最高的一项），先核实事实：`git fetch`、看 PR/Release/CI、看工作区有没有别人的未提交改动。
2. 写清楚：要解决的问题、证据、验收标准、不得回退的指标。
3. 独立分支或 worktree 内做最小改动。
4. 补对应测试；做真实转换（打包后的 `.app` / deb / zip，不是只在开发解释器里）、界面检查与性能对照。
5. 聚焦的 PR → 独立评审 → 必需检查全绿 → 合并 → 验证构建产物。
6. GitHub Release：资产校验值、干净安装、启动、一次代表性转换都验证通过后才算发布。
7. 更新 `docs/RELEASE_NOTES.txt`、本文件第 3–5 节（状态、基线、队列）。

每一轮必须产出以下之一：可验证的改进；有用的失败实验结论（写进第 6 节）；能影响决策的证据。

### 2.2 必须先问维护者的事

删除用户数据、破坏性迁移、改变仓库可见性、新的付费承诺（如 Apple Developer Program）、重大授权或许可证变化（如引入 GPL 组件）。

### 2.3 硬性禁止

- 绕过分支保护、伪造评审、关闭或放宽质量门禁、把跳过的测试当通过。
- 把草稿或未验证的构建称为「交付」；没有 Developer ID 与公证证据就写「已签名/已公证」。
- 上传用户文件或调用云端知识库；把维护者的个人身份写进任何公开内容（规则见本地 AGENTS.md）。
- 复制受限实现或竞品界面素材。

### 2.4 验证口径

- **样本**：合成样例为主（`scripts/create_fixtures.py` 及第 0.2 版新增的语料生成器）；区分「代表样本」与「留出样本」，调参只看代表样本，验收看留出样本。真实资料只用小份、只读，且不入库。
- **逐格式检查**：PDF 页数、逐页渲染比对、文本抽取一致；图片像素/尺寸/色彩/元数据；Office 页数与渲染比对；RAG 清单与哈希。
- **有损**：同时报告质量（如 SSIM/PSNR、文字层是否保留）与体积，不只报压缩率。
- **失败路径**：加密、损坏、同名冲突、低磁盘、取消、中断后续跑，每类至少一条自动化用例。
- **性能**：至少 3 次重复，报告中位数与波动；**测 PDF 转图片时必须设 `CHAMO_PAGE_CACHE=0`**，否则页缓存会让第二次运行只剩约 40%（见第 4 节）。
- **依赖**：版本锁定（`scripts/engine_deps.py`、`third_party/requirements.lock`）；升级依赖单独成 PR 并附回归结果。
- **多端功能单测**：按 `docs/CI_TESTING.md` 补测试并确认对应 CI 作业覆盖；它列出了每个必需检查覆盖什么、新功能必须补哪些用例、哪些部分 CI 覆盖不到。
- **CI 不等于产品测试**：CI 覆盖引擎与打包；macOS GUI 需在打包后的应用里点击验证（`-D CHAMO_DEBUG` 钩子与截图）。

## 4. 关键基线

### 4.1 本轮实测（Apple M1 Pro 10 核 / 32 GB，macOS 27.0.1，`build/Chamo.app` 0.1.0）

| 指标 | 结果 | 复跑方法 |
| --- | --- | --- |
| `.app` 体积 | **612 MB**：LibreOffice 470 MB（77%）、Python 运行时 136 MB、引擎 1 MB、界面二进制 2.8 MB | `du -sh build/Chamo.app/Contents/*` |
| Python 包前几名 | lxml 20 MB、Pillow 14 MB、cryptography 11 MB、pikepdf 7.9 MB、pypdfium2 7.2 MB、pypdf 3.9 MB、openpyxl 2.7 MB | `du -sh .../site-packages/*` |
| 引擎冷启动 | `chamo --help` 0.03–0.09 s；`import workbench` 0.04–0.10 s | `time` 3 次 |
| 120 页文字 PDF → PNG 150 dpi | **1.00 / 1.00 / 1.07 s**（页缓存关闭），产出 35 MB | 第 0.2 版要把它固化成基准脚本 |
| 同上，页缓存开启 | 第 2、3 次 0.44 s | 说明缓存生效，也说明基准必须关缓存 |

### 4.2 旧项目已有基线（同机，合成样例，可作对照起点）

| 指标 | 结果 |
| --- | --- |
| 2000 张小图片 | 引擎约 3.5 s，打包后约 4.3 s（分批与预编译前 70–139 s） |
| 3 个 PPTX → PDF | 约 4 s；LibreOffice 冷启 3.75 s、热启约 1.58 s |
| 文字型 vs 扫描型 PDF 分片 | 文字型：单进程 8 线程 200–207 页/秒，6 进程反而 150–164；扫描型：6 进程 114–125 页/秒，约 1.7–1.9× |
| 每页写后校验 | 吞吐约 -16%（192 → 162 页/秒），换来「写出的 PNG 一定可解码」，保留 |
| 无损 PDF 清理 | 普通 PDF 约省 3.8%；重复 PNG 图像约 21%（来自 Flate 重压）；重复 JPEG 0%；多次增量保存的反而变大 10.8% |
| 只重压已嵌入图像（不栅格化） | 0.997，基本无效（当时实现未真正替换图像流） |
| 文字型 PDF 栅格化 | 放大 164–491 倍并丢文字层 → 默认禁止 |
| Vision OCR（`.fast`，中英，200 dpi） | 约 135 ms/页；`.accurate` 在合成图上报 `unknownError`，未验收 |
| `RecognizeDocumentsRequest`（macOS 26+） | 首次 67.6 s 装载模型，热态 350–390 ms/页 |
| 安装包 | DMG 296 MB（旧 0.6.2）；deb 约 14–15 MB；Windows zip 约 31 MB |

### 4.3 竞品差距（官方页面 A 级证据；**均未安装实测**）

- 入口效率：Kumquat（拖放环、`kumquat` CLI、⌃⌥K）、Hazel（规则）、Dropzone（动作）、PDF Squeezer（Automator/CLI）把一次转换压到 1–2 步；Chamo 目前需要打开应用 → 选工具 → 加文件 → 开始。
- 压缩：ImageOptim 多引擎取最小；PDF Squeezer 有完整的压缩配置与并排对比。
- OCR 与结构化：Stirling、iLovePDF、Docling、Marker 都有；Chamo 没有。
- 工作流：Sejda Workflows、Stirling Pipeline。
- 未做：任何竞品的本机运行对比（D 级）。第 0.2 版起只对**开源/免费可得**的竞品做同口径实测；商业产品未实测就标「未实测」。

## 5. 版本队列

每个版本格式：**目标 / 依据 / 范围 / 验收 / 不得回退 / 风险与待决**。范围内某项被证据否定时，记录到第 6 节，不要硬做。

### 第 0 轮（前置）：发布 0.1.0

- **目标**：用 GitHub Actions 从干净环境构建并发布第一个 Release。
- **依据**：仓库尚无 Release；旧发布脚本已删。
- **范围**：`release.yml`（tag 触发）：macOS arm64 runner 用 `bootstrap_dependencies.py` 拉取并校验依赖 → `build_app.py` → `package_dmg.py`；复用现有 deb/zip 作业；生成 `SHA256SUMS.txt`；资产隐私扫描（构建机路径、个人身份）；先建草稿 Release，验证后再公开。
- **验收**：从 Release 页面重新下载全部资产，SHA-256 与清单一致；DMG 只读挂载、复制安装、启动、PDF 转图片与 PPTX 转 PDF 各一次；deb 在干净容器安装并转换；zip 在 Windows runner 解压并转换；`.pyc` 与资产中无构建机路径。
- **不得回退**：CI 现有 5 个作业全绿。
- **待决**：公开发布前问维护者。

### 0.2.0 · 验证与基准底座（准、快、小的度量衡）· 进行中

> 状态（2026-10-22）：**部分完成**。已做：确定性合成语料（smoke / representative / holdout 三套）、统一运行器（N 次重复、中位数与波动、强制关页缓存、记录机器与依赖版本、JSON 输出）、逐格式质量检查器（逐页与 pdfium 同 dpi 比对、无损图片逐像素、拆分页并集、压缩后文字层、RAG 导出哈希），以及「五类作弊必须被判红」的测试（PR #18）。
> 未做：① 第 4.1 节数字的复现（需要打包后的 `.app`，等发布流水线）；② 同口径竞品实测（需要把开源工具装进 runner）；③ CI 里的独立基准作业（要改 `.github/`，属受保护路径）。

- **目标**：让后面 19 个版本的每个「更快/更小/更准」都有可复跑的同口径证据。
- **依据**：旧研究的基准脚本在仓库外，口径不统一；本轮发现页缓存会让 PDF 基准失真 2.3 倍。
- **范围**：`bench/` 目录（或 `scripts/bench_*.py`）：确定性的合成语料生成器（文字型/扫描型/混合 PDF、PPTX/DOCX/XLSX、各类图片、边界样例），代表集与留出集分开；统一运行器（N 次重复、中位数/波动、关缓存、记录机器与依赖版本、JSON 输出）；逐格式质量检查器（渲染比对、文本抽取、像素/SSIM）；CI 中跑小规模冒烟（只报告不卡门禁，避免共享 runner 的噪声误判）。补一份同口径竞品对照：只选开源可得的（如 Kumquat、Stirling PDF 自托管）。
- **验收**：一条命令复现第 4.1 节全部数字，3 次结果波动 < 10%；质量检查器能识别人为注入的错误（少一页、换一张图、文字层丢失）。
- **不得回退**：测试数不减少；现有 CI 时长增加 < 3 分钟。

### 0.3.0 · 安装包瘦身（小）

- **目标**：显著减小 macOS 安装包，Office 渲染结果不变。
- **依据**：`.app` 612 MB，其中 LibreOffice 470 MB；旧项目已从 645 MB DMG 剪到 296 MB，仍有空间（语言包、帮助、未用模块、Python 标准库与包内测试数据）。
- **范围**：逐项剪裁实验（每项单独测量体积与回归）；评估 `lxml`、`cryptography` 是否只被少数路径使用，能否延迟导入或替换；DMG 压缩格式对比（ULFO/ULMO）。
- **验收**：Office 语料（含中日韩字体、公式、图表、WPS 格式）渲染结果与剪裁前逐页一致；DMG 与 `.app` 体积变化写入第 4 节。
- **不得回退**：Office 转换成功率与渲染一致性；冷启动时间。
- **风险**：剪掉字体或过滤器会让某些文档静默变差 → 必须用留出集验证，不能只看代表集。

### 0.4.0 · 一步到位入口

- **目标**：从 Finder 选中文件到得到结果 ≤ 2 步。
- **依据**：竞品对比中最大的产品缺口；现有 Finder 服务只「加入列表」。
- **范围**：Finder 服务/快速操作「用 Chamo 按上次规则转换」；拖到 Dock 图标且已有默认规则时直接开始；完成后系统通知 +「在 Finder 中显示」；失败时打开应用定位到异常项。默认规则必须可见、可改。
- **验收**：打包后的应用里点击验证 3 个入口；首次使用没有默认规则时进入普通流程而不是猜测；原件不动、同名不覆盖。
- **不得回退**：现有入口（开始页推荐、侧栏拖放、⌘K）。

### 0.5.0 · Office 吞吐（快）

- **目标**：批量 Office 转换明显提速，单个文件的结果不变。
- **依据**：LibreOffice 冷启 3.75 s、热启 1.58 s，进程启动是主要成本；常驻 soffice 旧研究判定风险高。
- **范围**：实验两条路并做同口径对比：① 同一 soffice 调用一次转换多个文件（摊薄启动）；② 每个 worker 的 profile 预热复用。批内任一文件失败时自动退回单文件模式，保持失败隔离与超时。
- **验收**：10/50 个 PPTX/DOCX 的总耗时对比（3 次）；输出逐页渲染一致；损坏文件混入批次时其他文件仍成功，且错误归属正确。
- **不得回退**：单文件超时与取消、进程树清理（`process_tree_mutation_check.py`）。

### 0.6.0 · 图片压缩多引擎（小·输出）

- **目标**：无损图片压缩追上 ImageOptim 一类工具的思路：多个无损方案取最小，结果像素一致。
- **依据**：当前无损优化只有 PNG 自写 IDAT 重压；旧实测 optimize=True 约省 17%。
- **范围**：评估 oxipng（MIT）、mozjpeg 的 jpegtran（BSD 类）作为随包二进制；无损路径一律像素 + 元数据校验；有损路径仍需主动选择并报告质量指标。
- **验收**：图片语料上的体积中位数与最差值对比；所有无损结果像素一致；新增二进制的许可写入 `docs/LICENSES.txt`；安装包增量在第 4 节记录。
- **不得回退**：批量 2000 张小图的耗时（允许为更好的压缩付出的时间要单独写明）。

### 0.7.0 · PDF 压缩：图像流替换（小·输出）

- **目标**：扫描型 PDF 在不栅格化文字的前提下真正变小。
- **依据**：旧实测「只重压嵌入图像」0.997，原因是没有真正替换图像流；栅格化文字型 PDF 会放大且丢文字层。
- **范围**：用 pikepdf 逐个替换图像 XObject（降采样/重编码，保留 SMask 与色彩空间）；按页面类型分派（复用 `engine/pageclass.py`）；屏幕/标准/打印三档；界面显示前后体积、DPI、质量指标。
- **验收**：扫描型语料体积比与 SSIM 报告；文字层与链接保留；文字型 PDF 不会变大（变大即保留原件并说明）；加密/签名 PDF 仍拒绝。
- **不得回退**：无损档的结果与 0.1.0 一致。

### 0.8.0 · OCR（实验性，仅 macOS）

- **目标**：为扫描 PDF 生成可搜索的文字层，标「实验性」。
- **依据**：竞品普遍具备；Vision `.fast` 约 135 ms/页，`.accurate` 曾失败。
- **范围**：Swift helper 调用 Vision，输出不可见文字层的新 PDF（原件不动）；语言选择；明确显示识别模式与限制。Windows/Linux 本版不提供，界面与 CLI 如实说明。
- **验收**：先用 20–50 份真实扫描件（只读、不入库）测字符准确率并写进记录；合成语料进 CI；`.accurate` 稳定后才可设为默认。
- **不得回退**：非 OCR 路径的速度与结果。
- **风险**：准确率不达标就停在实验性，并把结论写入第 6 节。

### 0.9.0 · RAG 结构导出

- **目标**：输出可检索的结构，而不仅是原样文件。
- **依据**：Docling/Marker/RAGFlow 的核心价值在结构；`RecognizeDocumentsRequest` 已实测可用（macOS 26+）。
- **范围**：新工具「结构导出」：Markdown（标题层级、列表、表格）+ JSONL（`source`、`page`、`bbox`、`heading_path`、`sha256`）。路径：PDF 文本层（pypdfium2，跨平台）为基础；macOS 26+ 叠加视觉结构；模型装载 67 s 需进度提示并在进程内复用。界面标明当前走的是哪条路径。严格模式规则不变（不隐式把 Word/PPT 转 PDF）。
- **验收**：合成语料的标题/表格/页码可核对；与 Docling 等开源工具在同一语料上做对比并如实报告。
- **不得回退**：RAG 严格模式的输出与清单格式。

### 1.0.0 · 稳定版

- **目标**：可以放心推荐给别人的版本。
- **依据**：0.2–0.9 的能力需要统一的数据安全与兼容性收口。
- **范围**：数据安全回归套件（取消、断电模拟、磁盘写满、外置盘拔出、同名竞态）；macOS 15/26/27 兼容矩阵；Windows/Linux 浏览器界面与 macOS 功能对齐表（不能对齐的明确标注）；请求/事件协议版本化文档（`protocol` 字段）；升级路径（旧状态目录兼容）。
- **验收**：矩阵中每格都有实测记录或「未测」标注；所有失败路径用例通过。
- **待决（需维护者决定）**：是否加入 Apple Developer Program（付费）以做 Developer ID 签名与公证。没有账号时 1.0 仍可发布，但必须继续写明「ad-hoc 签名、未公证」。

### 1.1.0 · 命名模板与输出规则

- 范围：`{名称}{页码}{日期}{规则}` 模板、实时预览、冲突仍走 `name (2)`；预设里保存模板。
- 验收：模板非法字符与超长名在三个平台的处理（`platform_names.py`）都有用例；绝不覆盖。

### 1.2.0 · 万级批次与空间预估

- 范围：1 万文件批次的暂停/恢复/只重试异常；开始前预估输出体积与所需空间，运行中低空间自动暂停（已有）与预估误差记录。
- 验收：1 万个合成文件端到端（耗时、RSS 峰值、界面流畅度）；预估误差中位数与最差值。

### 1.3.0 · 目标体积

- 范围：图片与 PDF 压缩「压到 ≤ X MB」，二分搜索参数；达不到时如实说明并给最接近的结果。
- 验收：多种目标值下结果 ≤ 目标或明确失败；质量指标随结果报告。

### 1.4.0 · 长图与多帧拆分

- 范围：PDF/PPT 转长图（按长度分段，规则显示在界面上）；GIF/TIFF/HEIC 多帧拆分。
- 验收：超长页数的分段正确、无裁切；内存峰值受控。

### 1.5.0 · Office 转换前审计与保真报告

- 范围：转换前检查缺失字体、隐藏幻灯片、备注、宏、外部链接、嵌入对象；结果中逐项列出「会变化什么」。
- 验收：语料中每类问题都能被识别；误报率记录。

### 1.6.0 · 可导出的处理报告

- 范围：批次报告导出 CSV/PDF：每个文件的来源与成品 SHA-256、保真标记、耗时、失败原因。
- 验收：报告可被独立脚本复核（哈希重算一致）。

### 1.7.0 · RAG 分块预览与表格导出

- 范围：导出前可视化分块边界，可调整长度/重叠；表格导出 CSV 并标注「结构来自识别，需复核」。
- 验收：调整后的分块与导出一致；表格单元格与语料真值对比。

### 1.8.0 · 压缩包安全解包

- 范围：ZIP（及评估 7z/RAR 的许可）解包后按规则处理成员；防路径穿越、压缩炸弹、符号链接逃逸、编码乱码。
- 验收：恶意样例全部被拒绝并说明原因；正常包成员与清单一致。

### 1.9.0 · 自动化接口

- 范围：CLI JSON 事件协议 v2（向后兼容 v1）；macOS 快捷指令/App Intents；可选的监视文件夹（默认关闭，有明确的耗电与权限说明）。
- 验收：协议有文档与契约测试；三个平台的 CLI 行为一致。

### 1.10.0 · 音视频探测与无损 remux

- 范围：先做容器/轨道/字幕探测与兼容容器间的无损 remux；不做转码。
- 验收：remux 后轨道、时长、帧数一致；不能称转码为无损。
- **待决（需维护者决定）**：FFmpeg 构建配置与许可（LGPL 动态链接，不启用 GPL/nonfree），以及安装包体积代价。

### 1.11.0 · 跨平台分发升级

- 范围：Windows 安装包与 winget、Linux AppImage 或 Flatpak 的可行性对比；应用内更新通道（校验签名与哈希后才替换，旧版本可回滚）。
- 验收：干净虚拟机/容器中安装、升级、回滚、卸载都实测通过。
- **待决**：Windows 代码签名证书（付费）。

## 6. 实验结论与否定记录

| 日期 | 结论 | 证据 |
| --- | --- | --- |
| 旧项目 0.3 前 | 「大 PDF 一律分片可快 5 倍」作废：文字型分片更慢，只有扫描型约 1.9× | `verify-ceiling` 两次运行 |
| 旧项目 0.3 前 | 无损 PDF 清理收益窄，不宣传压缩率 | `cleanup`、`cleanup-attribution` |
| 旧项目 0.3 前 | 常驻 LibreOffice 收益有限、风险高，暂缓 | `mixed` 冷/热启数据 |
| 2026-10-21 | PDF 基准必须关闭页缓存，否则第二次运行只剩约 40% | 第 4.1 节 |
| 2026-10-22 | 「把整页缩到 96×96 再算 SSIM」不足以判断两页是否相同：96% 白底、只有几行文字不同的两页会被判成同一页（CI 上被 `swapped-page` 用例抓到）。改为全分辨率平均差（阈值 1.0 灰阶）＋最差 1/16 块平均差（阈值 8.0） | PR #18 的三端 test-matrix |
| 2026-10-22 | OOXML 语料默认**不可复现**：openpyxl 保存时刷新 `docProps/core.xml` 的时间戳，且 zip 条目带保存时间。固定核心属性还不够，必须同时规范化 `docProps/*.xml` 与 zip 时间戳 | PR #18 的 macOS/Windows 失败与修复 |
| 2026-10-22 | macOS 上 `content.text` 计时门禁：把判据从中位数改成「每臂取最小、最多 8 对」后，配对波动从 ±17.8% 收到 ±8.9%，但 10 次里仍失败 1 次（ratio 0.944，判为慢 5.6%） | Issue #10，run 39740360476 |
| 2026-10-22 | 假设（未验证）：auto 臂比 off 多出的 5–6% CPU 可能来自内容判定本身（120 页文本 PDF 读一遍约 0.5–0.6 s），即 5% 预算可能小于功能的固定开销 | Issue #10 的算式，待用 `pageclass.classify()` 单独计时验证 |
